# اقتراح منتج بديل عند نفاد منتج في السلة

**التاريخ:** 2026-10-28. **المصدر:** فحص لوحة الإدارة، والـ API العام، ومهام Notion (لقطة 10-22). قراءة فقط.

## 1. ما شوهد في البنية الحالية
| العنصر | الوضع |
|---|---|
| **حقل "منتجات بديلة" أو "مشابهة" في المنتج** | ❌ غير موجود في صفحة تعديل المنتج، ولا في بيانات المنتج في الـ API |
| **رابط في الـ API للمنتجات المشابهة أو البديلة** | ❌ غير موجود (جرّبت `similar` و`related`، وكلاهما 404) |
| **إعداد للبدائل أو لسلوك السلة عند النفاد** | ❌ إعدادات النظام فيها فقط: حد أدنى للسلة، وحد أقصى للمنتجات، وحد "مخزون منخفض" |
| **إظهار المنتج "غير متوفر" عند نفاد الكمية** | ✅ موجود (مهمة منجزة) |
| **"نبّهني عند التوفر"** | ✅ موجود (حقل `notification_set`، ومهمة منجزة) |
| **"احفظ لوقت لاحق"** | ✅ موجود (حقل `is_save_for_later`) |
| **تواصل البائع مع العميل عند عدم توفر صنف** | ✅ موجود كإجراء يدوي (مهمة منجزة) |
| **صف "قد يعجبك أيضاً" في السلة** | ✅ موجود في التطبيق، لكنه اقتراحات عامة وليس بديلاً للمنتج الناقص (منطقه غير موثّق) |
| **الوسوم (tags) على المنتج** | ✅ حقل موجود يقبل نصاً، **يمكن استخدامه لتخزين البدائل مؤقتاً** |
| **مهمة في Notion** | "تحديث السلة واقتراح بدائل للمنتجات غير المتاحة": **لم تبدأ منذ 10-18، وبلا مسؤول** |

**الحكم:** **اقتراح البديل غير موجود في البنية الحالية، ويحتاج تدخلاً برمجياً.** الموجود الآن ثلاثة أشياء:
- إخفاء المنتج النافد أو وسمه "غير متوفر".
- "نبّهني عند التوفر".
- اتصال يدوي من البائع بالعميل.

## 2. ما نستطيع فعله الآن بلا برمجة
1. **منع الوصول للنفاد أصلاً:** معيارنا التوفر 99–100%، وأي بديل يبقى علاجاً. المطلوب مخزون حقيقي بدل القيمة المؤقتة 10، وحد "مخزون منخفض" يُخفي المنتج قبل نفاده.
2. **الاتصال اليدوي:** يُستخدم مع نص موحّد لموظف المتجر: "المنتج X غير متوفر، نقترح Y بنفس السعر أو أقل، توافق أو نسترد قيمته؟".
3. **تجهيز بيانات البدائل مسبقاً، وأنا أنفذه:** لكل منتج 2–3 بدائل محسوبة آلياً بهذه الشروط:
   - من نفس المربع.
   - بنفس الحجم أو قريب منه (±20%).
   - بسعر قريب (±15%)، والأولوية لنفس العلامة ثم الأقرب سعراً.

   تُحفظ كوسوم على المنتج (مثل `sub:JRN00001234`)، فتكون جاهزة لمحمد بلا جمع بيانات لاحقاً. **يحتاج موافقتك**، لأنه تعديل جماعي على المنتجات (قابل للتراجع).

## 3. ما يحتاج برمجة
### محمد (Backend)
- **رابط API للبدائل:** يقرأ البدائل المحفوظة. وإن لم توجد يحسبها من نفس المربع والحجم والسعر، ويستبعد غير المتوفر في متجر العميل.
- **فحص السلة:** عند فتح السلة وقبل الدفع، يُعلَّم كل منتج نفد مع بدائله.
- **تفضيل العميل لكل طلب:** "إذا لم يتوفر منتج": استبدله بأقرب بديل، أو اتصل بي، أو استرد قيمته. يُحفظ مع الطلب ويظهر للبائع.
- **تطبيق البائع:** عند التجهيز، اقتراح البديل حسب تفضيل العميل، وتعديل الطلب والمبلغ تلقائياً (الفرق يُسترد ولا يُضاف).

### عبيد (Flutter)
- **في السلة:** المنتج النافد بشارة "غير متوفر"، وتحته "بدائل مقترحة" (2–3 بطاقات) بزر "استبدال" يحل البديل محل الأصلي بنفس الكمية.
- **في المراجعة:** اختيار "إذا لم يتوفر منتج" (ثلاثة خيارات). هذه بطاقة موجودة أصلاً في تصميم رحلة الدفع، موسومة "بعد A7".
- **في صفحة المنتج النافد:** "نبّهني عند التوفر" (موجود) + "منتجات مشابهة".

## 4. التصنيف والأولوية
| البند | التصنيف | السبب |
|---|---|---|
| مخزون حقيقي وحد مخزون منخفض | **MVP Now** (تشغيل) | يمنع المشكلة من أصلها، ومعيار التوفر 99–100% |
| النص الموحّد للاتصال اليدوي | **MVP Now** (تشغيل) | يعمل اليوم |
| تجهيز بيانات البدائل كوسوم | **MVP Now** (محتوى، أنا) | بلا برمجة، ويختصر عمل محمد |
| تفضيل العميل عند عدم التوفر | **MVP Now** (Backend + Flutter) | سياسة الاسترجاع المنشورة تعد به ضمناً |
| بدائل داخل السلة، واستبدال آلي عند التجهيز | **Next** | بعد تاب |

## 5. قرارات مطلوبة من فضل
1. السلوك الافتراضي عند عدم التوفر: **استبدال بأقرب بديل** (كما في كيتا)، أم **الاتصال بالعميل**؟
2. قاعدة السعر: البديل الأغلى يُحسب على العميل، أم يُعطى بسعر الأصلي؟ أفضل ممارسة: **بسعر الأصلي أو أقل، ولا يُحمَّل العميل فرقاً**.
3. الموافقة على أن أجهّز بيانات البدائل وأحفظها كوسوم على المنتجات.

## 6. فحص الوسوم (Tags) عملياً (2026-10-28)
**الاختبار:** أضفت وسماً تجريبياً `jrnsubtest` إلى منتج الموز (1296) من لوحة البائع، ثم فحصت الـ API، ثم حذفته. عاد المنتج كما كان.

| السؤال | النتيجة |
|---|---|
| هل يوجد حقل للوسوم؟ | ✅ في لوحة البائع، داخل خطوات صفحة تعديل المنتج (`product-tags-input`)، وفي قالب الرفع الجماعي (عمود `tags`) |
| هل يُحفظ؟ | ✅ نعم |
| هل يعيده الـ API مع المنتج؟ | ✅ يعيده في حقل `tags` |
| هل يمكن البحث به؟ | ✅ `products/search?search=<الوسم>` أعاد المنتج الموسوم وحده |
| هل يعرض التطبيق بدائل منه تلقائياً؟ | ❌ لا يوجد في التطبيق أو الـ API منطق يقول "إذا نفد المنتج اعرض ما يشاركه الوسم" |
| هل الوسوم الحالية مستخدمة؟ | لا. المنتجات بلا وسوم، مثل الموز (`tags: []`) |

**الخلاصة:** **الوسم يخدمنا كطبقة بيانات جاهزة، لا كميزة تعمل وحدها.**
- **بلا برمجة:** نستطيع وضع **وسم مجموعة** على كل منتجات قابلة للتبادل، مثل `grp-milk-full-2l` لكل حليب كامل الدسم 2 لتر، و`grp-water-330x40`. يُحفظ في المنصة ويُبحث به.
- **ما يبقى برمجياً (أبسط مما في القسم 3):**
  - **عبيد:** عند نفاد منتج في السلة، يستدعي البحث بوسم مجموعته، ويعرض المتوفر منها بديلاً.
  - **محمد:** استبعاد المنتج النافد من النتيجة، وترتيبها حسب قرب السعر، وتأكيد أن البحث يحترم متجر العميل.

**تنبيهان:**
1. يُتحقق على الجوال: هل يعرض التطبيق الوسوم للعميل في صفحة المنتج؟ إن كان يعرضها، فتُكتب بصيغة لا تزعج العميل أو يُخفيها عبيد.
2. البحث بالوسم مطابقة نصية، فيُستخدم بادئة ثابتة فريدة (`grp-`) حتى لا يختلط بأسماء المنتجات.

**الأداة:** `catalog/scripts/platform/product_tag.cjs` تضيف أو تحذف وسماً لمنتج. والتعبئة الجماعية تكون عبر عمود `tags` في الرفع الجماعي، أو بالأداة على دفعات.
